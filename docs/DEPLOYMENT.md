# Render + Neon + Android APK testing

This guide deploys the current **test environment** with SMTP email OTPs and
simulated payments. No real money moves. Do not use it for live customers. The production
startup guards remain enabled; `NODE_ENV=development` is deliberate for this
test environment, and must be changed along with live payment provider configuration
before a public production launch.

## 1. Neon credentials

In the Neon console, obtain the two connection strings for the same database:

- `DATABASE_URL`: pooled connection (hostname includes `-pooler`).
- `DIRECT_URL`: direct connection (disable connection pooling in Connect).

Keep Neon SSL options on both. Runtime queries use the pooled URL; Prisma CLI
migrations use the direct URL. Never commit either connection string. Rotate
the database password shared in chat before the deployment and use the new
values in Render. Rotate the Gmail app password shared in chat as well. Local
`.env` and `.env.render` files are ignored by Git.

## 2. Deploy the backend on Render

Connect the GitHub repository `afropenthouse/VerySure` to Render.

**Blueprint option:** choose New > Blueprint and select the repository. Review
`render.yaml`. It requests a **paid Starter web service and 1 GB persistent
disk** so report photos survive restarts. Enter `DATABASE_URL`, `DIRECT_URL`,
your service's HTTPS `PUBLIC_API_URL`, `SMTP_USER`, `SMTP_PASS`, and `MAIL_FROM`
when requested. If Render assigns a
different service address, update `PUBLIC_API_URL` to that exact address and
redeploy. Secrets and the test account password are generated by the Blueprint.

**Manual Web Service option:** use these settings. Leave Root Directory blank
because the project uses a root npm workspace and shared package lock.

| Setting           | Value                                                                  |
| ----------------- | ---------------------------------------------------------------------- |
| Runtime           | Node                                                                   |
| Branch            | main                                                                   |
| Root Directory    | Leave blank                                                            |
| Build Command     | `npm ci --include=dev && npm run db:generate && npm run build:backend` |
| Start Command     | `npm run db:migrate && npm start --workspace backend`                  |
| Health Check Path | `/health`                                                              |
| Disk mount path   | `/var/data`                                                            |
| Disk size         | 1 GB                                                                   |

Add environment variables from `render.yaml`, with three independent random
secrets of at least 32 characters and a private `SEED_PASSWORD` of at least 12
characters. A private `backend/.env.render` file is prepared locally as an
import template; update its rotated database credentials and actual Render URL
before using Render's environment import. Do not import it into Expo.

Render supplies `PORT`; the API listens on `0.0.0.0`. Migrations run before the
server starts and fail the deployment if they cannot complete. A single service
instance is intended for this test setup. Do not use schema reset or `db push`.

A free service blocks outbound SMTP ports 465 and 587, so Gmail OTP delivery
requires a paid service. For a free temporary demo, set `OTP_PROVIDER=demo`,
omit the disk and set `UPLOAD_DIR=./uploads`; uploaded photos will be lost on
restart or redeploy. Alternatively, configure the existing Resend HTTP adapter.

SMTP uses TLS on port 465 (or mandatory STARTTLS on other ports), with bounded
timeouts. Use a Gmail app password, not your normal login password. Set
`MAIL_FROM` to the sender name/address you want users to see; it must be allowed
by your SMTP account. The local deployment template retains the sender name
you supplied. Email OTPs are not returned in API responses. SMTP delivery from
Render must still be tested after deployment; no live OTP email was sent during
local validation.

After deployment, open `https://YOUR-RENDER-ADDRESS/health`. Expected result:

```json
{ "status": "ok", "database": "postgresql" }
```

## 3. Add test accounts and sample products

Run once in the Render service Shell (paid service):

```sh
npm run db:seed
```

This creates the consumer, retailer, manufacturer, NAFDAC, SON and admin test
accounts listed in README.md. Their password is the private `SEED_PASSWORD`
from Render's environment settings. Rerunning does not overwrite accounts or
wallet balances. Seeding is never part of automatic deployments.

## 4. Connect Expo and build the APK

Your Expo Go login is the same Expo account used by EAS. Expo Go itself does
not generate the APK. In PowerShell:

```powershell
cd C:\Users\HP\Desktop\VerySure\frontend
npx eas-cli@latest login
npx eas-cli@latest init
```

Create/link the Verysure project. Because `app.config.ts` is dynamic, if EAS
cannot write the project ID automatically, add the exact ID it prints to the
returned config object:

```ts
extra: { eas: { projectId: "YOUR-EXPO-PROJECT-ID" } },
```

Then set the real Render URL and build:

```powershell
npx eas-cli@latest env:set --name EXPO_PUBLIC_API_URL --value https://YOUR-RENDER-ADDRESS --environment preview --visibility plaintext
npx eas-cli@latest build --platform android --profile preview
```

Accept EAS-managed Android signing and generation of a keystore on the first
build. Save account access and signing credentials for subsequent releases.
The existing preview profile produces a standalone APK: no Metro server or
Expo Go is needed to run it. No Google Play developer account is needed for
direct APK installation. Download the APK from the build link and share it
with testers. On Android, allow installation from the browser/file manager
when prompted. An Android emulator can install the same APK by drag-and-drop.

If you change the embedded API URL, create a new APK. Backend-only changes
deploy through Render and do not require an APK rebuild unless the API contract
also changes.

## 5. Test on a real phone

Check registration/email OTP (including inbox/spam), login/logout, role access, camera scanning, the
sample code `VS-EMZR-2026-0001`, scan history, ten free scans then wallet charges,
demo top-ups, transfers, photo/location reports and regulator replies. Test
different accounts on two devices and confirm reports/photos survive a backend
restart. Keep the test APK and demo account passwords within your test group.
